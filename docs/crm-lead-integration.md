# 차선생 CRM 리드 연동 계약 (확정본)

확정일: 2026-08-13 · 상대: 차선생 CRM(제임스) · 상태: **계약 확정, 구현 대기**

홈페이지 폼 제출을 CRM 고객으로 자동 등록한다. 두 차례 문서 교환으로 아래 내용이 확정됐다.

## 엔드포인트

```
POST https://crm.mrcha.app/api/homepage/lead
Header: x-homepage-secret: <시크릿>
Body:   multipart/form-data
```

**브라우저에서 직접 호출하지 않는다.** 시크릿을 쓰므로 반드시 서버(Workers)에서 호출한다.
시크릿은 Workers Secret으로만 보관하고 저장소·문서·메신저에 남기지 않는다.

## 필드

공통

| 필드 | 필수 | 출처 |
|---|---|---|
| `type` | ✅ | `consult` 또는 `quote` (아래 매핑) |
| `submissionId` | ✅ | `contact_submissions.id` (UUID v4) — **접두사 없이 원본 그대로** |
| `name` | ✅ | `name` |
| `phone` | ✅ | `phone` (하이픈 유무 무관, CRM이 숫자만 추출) |
| `inquiry` | | `message` |

`type=consult` 전용

| 필드 | 출처 |
|---|---|
| `desiredModel` | `car` (브랜드·모델·색상 자유 입력) |
| `purchaseMethod` | `methods[0]` — `운용리스｜장기렌트｜할부｜일시불` |
| `purchaseTiming` | `pay_period[0]` — `이번 달｜다음 달｜3개월 이내｜미정` |

`type=quote` 전용

| 필드 | 출처 |
|---|---|
| `file1`, `file2` | `attachments[]`의 R2 객체를 읽어 multipart 본문으로 직접 전송 |

선택지 문자열은 **띄어쓰기까지 정확히 일치**해야 한다. 목록 밖 값이 오면 CRM이 그 항목만 비우고 나머지는 등록한다.
우리 쪽은 서버 화이트리스트로 검증하므로 목록 밖 값은 애초에 제출되지 않는다.

## 폼 매핑

| 홈페이지 폼 | `form_key` | `type` |
|---|---|---|
| 신차 맞춤 컨설팅 | `consulting-new-car` | `consult` |
| 견적서 비교분석 | `analysis` | `quote` |

- 중고차 맞춤 컨설팅은 신차로 301 통합했다(중복 페이지).
- 차량시공 문의는 시공 사업 미운영으로 폐기했다. CRM 연동 대상이 아니다.
  CRM의 상태 흐름(신규→상담→견적→계약→출고→정산)이 신차 판매 전용이라, 시공 문의를 고객으로 넣으면
  견적을 만들지 않는 고객이 쌓여 방치 고객·전환율 지표가 왜곡된다는 것이 상대측 설명이다.
  나중에 필요해지면 CRM에서 `type=install` 처리를 추가하기로 했다.

## 파일

- 형식: **jpg·jpeg·png·pdf 4종**. webp로 넓히지 않는다(상대측이 불필요하다고 확인).
- 확장자가 아니라 **파일 시그니처(매직바이트)로 검증**한다. 현행 유지 요청받음.
- 용량: 파일당 10MB 이하, 최대 2개.
- 전달 방식은 **multipart 본문 직접 전송**으로 확정. 서명 링크 방식은 반려했다 —
  링크가 7일 후 만료되는데 CRM은 파일을 계속 보관해야 하므로, 어차피 수신 시점에 내려받아야 한다.
  링크를 거치면 단계와 실패 지점만 늘어난다.

## 응답

| 코드 | 의미 | 처리 |
|---|---|---|
| 201 | 등록 완료 | 성공 |
| 200 | 같은 `submissionId` 재전송 (`duplicate:true`) | **성공으로 처리** |
| 400 | 필수 누락·형식 오류 | 재시도해도 무의미 — 기록 후 알림 |
| 401 | 시크릿 불일치 | 설정 오류 — 기록 후 알림 |
| 404 | 라우트 미배포 | **재시도 대상** (아래 참고) |
| 413 | 용량 초과 | 재시도 무의미 |
| 415 | 허용되지 않는 형식 | 재시도 무의미 |
| 503 | 연동 미설정 | **재시도 대상** (배선 전·시크릿 교체 중 발생) |
| 기타 5xx | 상대측 장애 | 재시도 대상 |
| 네트워크 오류 | 도달 실패 | 재시도 대상 |
| 3xx | 설정 문제 | 재시도 무의미 |

**404를 재시도 대상으로 둔 이유** — 계약서 원문에는 미설정 상태를 503으로 규정했으나, 실측해 보니 라우트가 배포되기 전에는 404가 온다.

```
POST https://crm.mrcha.app/api/homepage/lead  →  404 {"error":"Not found"}
GET  https://crm.mrcha.app/                   →  200
```

도메인은 살아 있고 라우트만 없는 상태다. 우리가 직접 지정한 엔드포인트에서 나는 404는 **배포·라우팅 상태**이지 페이로드 문제가 아니다. 400·413·415가 "이 요청은 앞으로도 받아들여지지 않는다"인 것과 성격이 다르다.

404를 영구 실패로 두면, 상대측 배포 전에 들어온 리드가 전부 낙인찍히고 배포 후에도 자동으로 따라잡히지 않는다. 시도 횟수 상한이 있으므로 URL이 영영 틀린 경우에도 무한 재시도가 되지는 않는다.

`401`은 재시도 대상이 아니다. 시크릿이 틀린 것은 사람이 고쳐야 하고, 다시 보내봐야 같은 거부만 반복된다.

이 분류는 **우리 쪽 재시도 정책**이며 상대측 API 동작을 바꾸지 않는다. 계약 변경이 아니다.

## 멱등과 재시도

`submissionId`가 멱등 키다. 같은 값으로 몇 번을 보내도 고객은 하나만 생기고,
두 번째부터 `200` + `duplicate:true`가 온다. 따라서 실패 시 같은 ID로 재시도해도 안전하다.

우리 쪽 설계:

1. 제출 시점에 CRM 호출을 시도한다. **성공하면** `crm_synced_at`·`crm_record_id`를 기록한다.
   (이 두 컬럼은 연동을 염두에 두고 처음부터 스키마에 만들어 두었다.)
2. 실패하면 `crm_synced_at`을 null로 남기고 `crm_error`·`crm_attempts`·`crm_last_attempt_at`을 갱신한다.
   (마이그레이션 `0002_crm_sync_columns.sql`. 이 세 컬럼이 없으면 "아직 못 보냄"과
   "영구 실패"를 구분할 수 없어 재시도가 영원히 반복된다.)
3. **Cloudflare Cron으로 미동기 건을 주기적으로 재전송**한다.
   재시도는 **30분 간격, 최대 8회**다. 간격을 두는 이유는 예산이 Cron 주기에 종속되지 않게 하기 위함이다 —
   횟수만 세면 Cron이 1분마다 돌 때 8분 만에 소진되어, 그보다 긴 장애에서 리드가 영구히 멈춘다.
   30분 × 8회이므로 Cron 주기와 무관하게 **최소 4시간**의 재시도 예산이 보장된다.
4. 상한을 소진하면 담당자에게 알린다.

**시크릿의 유무가 켜짐/꺼짐 스위치다.** `CRM_HOMEPAGE_SECRET`이 없으면 전송을 시도조차 하지 않으므로
시도 횟수가 늘지 않고 실패로 기록되지도 않는다. 상대측 엔드포인트가 배포되기 전에는 운영에서 시크릿을
빼두는 것이 맞다 — 그래야 그동안 들어온 리드가 재시도 예산을 소진하지 않고, 시크릿을 넣는 순간
Cron이 밀린 건을 한 번에 따라잡는다.

`crm_error`에는 **상태 코드와 기계식 코드만** 저장한다. 상대측 응답 본문은 저장하지 않는다 —
400 응답이 잘못된 필드를 되비추는 것이 일반적이라, 본문을 남기면 고객 이름·전화번호가
DB 컬럼과 Workers 로그에 쌓인다.

리드는 어떤 경우에도 사라지지 않는다. 홈페이지는 **DB 저장을 성공의 기준**으로 삼으므로,
CRM이 응답하지 않아도 고객에게는 정상 접수로 응답되고 데이터는 Supabase에 남는다.

## 진행 순서

1. ~~계약 확정~~ ✅ 2026-08-13
2. **CRM 측 엔드포인트 구현·배포** ← 현재 여기 (상대측 작업)
   시크릿은 2026-08-13에 먼저 전달받았으나 **엔드포인트는 아직 배포 전이다**(실측: 404).
   그래서 운영 Workers Secret에는 일부러 넣지 않았다. 배포 완료 연락을 받으면
   `wrangler secret put CRM_HOMEPAGE_SECRET` 한 번으로 가동된다.
3. 홈페이지 측 연동 구현 (우리)
4. 임시 도메인 `dlas.dolcejian.workers.dev` 에서 테스트 제출 1건, 양측 확인
5. 운영 도메인 전환 후 재검증

과거 리드 소급 전송은 불필요하다(DB에 실제 리드가 없다).

**상대측 연락을 기다리는 상태다.** 시크릿이 오면 `wrangler secret put CRM_HOMEPAGE_SECRET` 으로 등록한다.
