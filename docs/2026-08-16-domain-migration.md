# dlas.co.kr 도메인 이전 기록 (2026-08-16)

WordPress 기반 운영 사이트를 Astro + Cloudflare Workers로 옮긴 마지막 단계 —
**도메인 전환**의 전 과정을 기록한다. 포트폴리오용으로 옮겨 쓸 수 있도록 배경과 판단 근거까지 남긴다.

---

## 1. 배경

DL오토솔루션의 사업장 사이트 `dlas.co.kr`은 카페24 호스팅 위에서 WordPress(Salient 17.2.0)로
운영되고 있었다. 이를 Astro 정적 사이트 + Cloudflare Workers로 **100% 동일하게 포팅**한 뒤,
임시 주소(`dlas.dolcejian.workers.dev`)에서 검증을 마친 상태였다.

남은 것은 실제 도메인을 옮기는 일이었다. 운영 중인 사이트이므로 제약이 분명했다.

- **회사 메일이 같은 도메인을 쓴다.** MX가 Google Workspace를 가리킨다. 메일이 끊기면 사고다.
- **검색 유입이 매출 경로다.** 색인과 소유확인이 끊기면 안 된다.
- **컨택폼이 유일한 리드 수집 채널이다.** 조용히 죽으면 알아차릴 방법이 없다.

### 이전 대상 아키텍처

| 구분 | 이전 전 | 이전 후 |
|---|---|---|
| 웹 | 카페24 (WordPress + Salient) | Cloudflare Workers (Astro 정적 31페이지) |
| DNS | 카페24 네임서버 | Cloudflare |
| 폼 저장 | WordPress DB | Supabase |
| 첨부 파일 | 서버 파일시스템 | Cloudflare R2 + 7일 서명 링크 |
| 알림 메일 | WP Mail | Resend |
| 봇 방어 | 없음 | Turnstile + 3계층 속도 제한 |
| CRM | Zmes 플러그인 | 차선생 CRM 자체 연동 |

## 2. 전략 — 되돌릴 수 없는 것과 되돌릴 수 있는 것을 분리한다

도메인 이전에서 가장 위험한 성질은 **네임서버 변경이 느리고 되돌리기 어렵다**는 점이다.
전파에 최대 48시간이 걸리므로, 잘못되면 그 시간만큼 사고가 지속된다.

그래서 전환을 두 단계로 쪼갰다.

### 1단계 — 네임서버만 옮긴다 (사이트는 그대로)

Cloudflare 영역에 **카페24와 완전히 동일한 레코드**를 복제하고,
A 레코드는 여전히 카페24 서버(`183.111.242.14`)를 가리키게 둔 채 네임서버만 교체했다.

이 상태에서는 어느 리졸버가 어느 네임서버를 보든 **답이 같다.** 전파가 섞여 있는 동안에도
사이트와 메일이 조금도 바뀌지 않는다. 느리고 위험한 단계에서 위험을 0으로 만든 것이다.

### 2단계 — Workers 커스텀 도메인을 붙인다 (실제 전환)

전파가 끝난 뒤 워커를 연결했다. 이 작업은 **반영도 롤백도 몇 초**다.
즉 "실제로 사이트가 바뀌는 순간"을 빠르고 되돌릴 수 있는 쪽으로 몰아넣었다.

## 3. 사전 준비 — 추측하지 않고 실측한다

기존 DNS 설정을 문서나 화면이 아니라 **권한 네임서버에 직접 질의해서** 확보했다.

```
A     dlas.co.kr    183.111.242.14
CNAME *             dlas.co.kr        (와일드카드)
CNAME www           dlas.co.kr
MX    dlas.co.kr    1 SMTP.GOOGLE.COM
TXT   dlas.co.kr    google-site-verification=...
TXT   dlas.co.kr    v=spf1 ip4:183.111.242.14 ~all
```

### 실측이 판단을 뒤집은 사례 — 와일드카드

와일드카드 레코드가 있어서 임의 서브도메인이 전부 응답했다. 처음에는 "그대로 복제해야 한다"고
적어두었는데, 실제로 찔러 보니 결과가 달랐다.

```
mail.dlas.co.kr    http=403   https=연결 실패
shop.dlas.co.kr    http=403   https=연결 실패
무작위 서브도메인    http=403   https=연결 실패
```

**응답만 할 뿐 아무것도 서빙하지 않는** 카페24 기본값이었다. 복제하면 임의 서브도메인이
워커로 유입되어 혼란만 생긴다. 복제하지 않기로 뒤집었다.

### 실측이 찾아낸 기존 결함

- **`www`는 apex로 301**을 보내고 있었다 → 이전 후에도 재현해야 한다.
- **SPF가 틀려 있었다.** MX가 Google인데 SPF에 `include:_spf.google.com`이 없어
  발신 메일이 softfail 판정을 받고 있었다. 이전과 무관한 기존 버그다.
- **Google Workspace DKIM 미설정**, DMARC 없음.

### 조용히 사이트를 죽일 뻔한 것 — Turnstile 호스트 제한

Turnstile 위젯의 사이트키에는 **허용 호스트 목록**이 박힌다. 임시 주소만 등록된 상태로
전환하면 새 도메인에서 토큰 발급이 실패한다.

이 실패가 위험한 이유는 **서버가 `200 + status:"spam"`을 돌려주기 때문**이다.
CF7은 non-2xx를 받으면 화면에 아무 문구도 못 띄우므로 4xx를 쓸 수 없어 그렇게 설계했는데,
그 결과 **거절이 정상 응답과 같은 형태**가 된다. 모니터링에도 잡히지 않고, 방문자에게만
"스팸으로 판단되었습니다"가 뜬다.

전환 **전에** 호스트 목록에 새 도메인 두 개를 추가했다.

## 5. 전환 중 발견해 해결한 문제

### 5-1. 정적 자산이 워커보다 먼저 처리된다

`www` → apex 301을 워커 코드로 구현하고 배포했는데 동작하지 않았다.
조사해 보니 경로에 따라 결과가 갈렸다.

```
/                      200   ← 워커가 실행되지 않음
/about/                200   ← 같음
/wp-json/.../feedback  301   ← 워커 실행됨
```

Cloudflare Workers는 `assets` 바인딩이 있으면 **정적 파일에 매칭되는 요청을 워커보다 먼저
처리한다.** 실제 페이지는 워커에 닿지도 않으므로 코드로는 호스트 리다이렉트를 걸 수 없다.

→ **존 레벨 리디렉션 규칙**으로 옮겨 해결했다.

### 5-2. `www`에서 POST를 리다이렉트하면 폼이 통째로 죽는다

리다이렉트를 만들 때 "301은 POST를 본문 없는 GET으로 바꿔 제출을 삼킨다"고 판단해
308을 썼다. **308이 더 나빴다.**

`www`에서 폼을 열면 action이 상대경로라 제출도 `www`로 간다. 거기서 308을 주면
apex로 가는 **교차 출처 리다이렉트**가 된다. 브라우저는 따라가지만 apex가
`Access-Control-Allow-Origin`을 주지 않으므로 fetch가 실패하고,
CF7은 성공도 실패도 아닌 채로 **스피너만 계속 돌린다.**

운영에서 실제로 재현됐고, 실제 제출 시도로 발견했다.

→ **문서 요청(GET/HEAD)만 리다이렉트**하도록 고쳤다. POST는 같은 호스트에서 처리한다.
Origin과 Host가 일치하니 CSRF 검사도 통과하고, 페이지 로드 시점의 301 덕분에
대부분의 방문자는 애초에 apex에서 폼을 연다.

이 판단은 존 레벨 규칙에도 그대로 반영했다.

```
(http.host eq "www.dlas.co.kr"
 and (http.request.method eq "GET" or http.request.method eq "HEAD"))
```

### 5-3. 전파 중에는 검색엔진이 옛 서버를 본다

네이버 소유확인(메타태그)과 사이트맵 제출이 실패했다. 원인은 우리 서버가 아니었다.

```
카페24 원본 (네이버가 보던 곳)   메타태그 없음 → 인증 실패
Cloudflare (실제 운영)          메타태그 있음, 크롤러 UA로도 200
```

**전환 직후에 검색엔진 제출을 하면 안 된다**는 교훈. 다만 소유확인은 우회로가 있었다 —
파일 인증용 파일이 **양쪽 서버 모두에 존재**했기 때문에, 파일 방식으로 바꾸니 즉시 통과했다.

사이트맵은 새 서버에만 있어서 우회가 불가능했고, 전파 완료 후 재제출로 해결했다.

### 5-4. 커스텀 도메인은 수동 DNS 레코드와 공존하지 않는다

```
Hostname 'dlas.co.kr' already has externally managed DNS records (A, CNAME, etc).
```

1단계에서 일부러 남겨둔 A 레코드가 커스텀 도메인 연결을 막았다. 지우고 붙여야 하는데
그 사이 몇 초간 해당 호스트가 죽는다. `www`를 지우고 붙이지 않은 채로 두면 사이트가 안 열린다.

→ 두 창을 미리 띄우고 연달아 처리해 공백을 최소화했다.

### 5-5. 로컬 DNS 캐시가 진단을 방해한다

`dig`는 새 IP를 보여주는데 `curl`은 옛 IP로 붙는 상황이 발생했다.

```
dig +short A dlas.co.kr              104.21.53.152 172.67.214.155
dscacheutil -q host -a name ...      183.111.242.14      ← 시스템 리졸버
curl -w '%{remote_ip}'               183.111.242.14
```

브라우저에서 `ERR_QUIC_PROTOCOL_ERROR`가 났던 것도 같은 원인이었다.
IP를 고정해 연결하는 방식(`curl --resolve`)으로 서버 상태와 클라이언트 캐시를 분리해 진단했다.

### 5-6. 발신 메일 링크가 제3자를 경유하고 있었다

첨부 다운로드 링크가 이렇게 왔다.

```
https://vw9jhtlx.r.us-east-1.awstrack.me/L0/https:%2F%2Fdlas.co.kr%2Fapi%2Ffile%2F...
```

메일 서비스의 클릭 추적 기능이 모든 링크를 감싸고 있었다. 이 URL에는
**고객 견적서 파일에 접근할 수 있는 HMAC 토큰**이 들어 있어, 클릭할 때마다
제3자 로그에 토큰이 남는다.

자체 도메인을 인증해 발신 주소를 바꾸자 래핑이 사라졌다.

## 6. 함께 정리한 것

도메인을 우리가 관리하게 되면서 그동안 손댈 수 없던 것들을 함께 정리했다.

| 항목 | 처리 |
|---|---|
| SPF | `v=spf1 include:_spf.google.com ~all` — 오래된 softfail 결함 해소 |
| DMARC | `v=DMARC1; p=none; rua=...` 신규. 리포트 수집부터 시작 |
| 발신 도메인 | Resend에 `dlas.co.kr` 인증(도쿄 리전). `noreply@dlas.co.kr`로 전환 |
| 메일 TLS | Opportunistic → **Enforced**. 고객 성함·연락처·견적서 링크가 담긴 메일이다 |
| 옛 사이트맵 | 원본이 거느리던 자식 3개를 301로 이어붙여 수집 오류 차단 |
| WAF 속도 제한 | 폼 엔드포인트에 엣지 레벨 차단 추가 |

발신 경로가 깔끔하게 분리된 것도 확인했다.

```
루트          → Google Workspace  (회사 메일)
send. 서브도메인 → Amazon SES        (시스템 알림 메일)
```

### WAF 규칙에서 주의한 점

```
(http.request.uri.path contains "/wp-json/contact-form-7/"
 and http.request.method eq "POST")
```

`POST` 조건이 핵심이다. CF7 자바스크립트는 **같은 경로로 스키마 GET**을 보내기 때문에,
메서드를 못 박지 않으면 폼 페이지를 여러 개 여는 것만으로 카운트가 오른다.

규칙 검증도 실측으로 마쳤다.

```
연속 POST 10회차          → 429 차단
차단 중 GET 페이지         → 전부 200 (일반 방문자 무영향)
90초 후                   → 200 정상 복구 (차단이 굳지 않음)
```

다만 WAF 차단은 429를 돌려주므로 **CF7이 화면에 아무 문구도 띄우지 못한다.**
사람이 낼 수 없는 속도라 오탐 가능성은 사실상 없지만, "폼을 눌러도 반응이 없다"는
문의가 들어오면 이 규칙을 가장 먼저 의심해야 한다는 점을 기록해 두었다.

### 아직 판정할 수 없는 것

**검색 색인 유지 여부는 며칠 뒤에야 알 수 있다.** 전환 시점의 기술 지표는 모두 정상이지만,
검색엔진이 사이트를 다시 훑는 데 시간이 걸린다. 3~7일 뒤 Search Console의 색인 페이지 수를
확인하는 것이 이 이전의 최종 판정이다.

옛 호스팅은 전파 잔여분을 위해 2주간 유지한다.

## 8. 남긴 원칙

- **되돌릴 수 없는 작업과 실제 변경을 분리한다.** 느린 단계에서는 아무것도 바꾸지 않는다.
- **문서가 아니라 응답을 믿는다.** 와일드카드 복제 판단은 실제로 찔러 보고 뒤집혔다.
- **조용히 실패하는 경로를 먼저 의심한다.** 거절이 200인 설계는 관측을 어렵게 만든다.
- **서버 상태와 클라이언트 캐시를 분리해 진단한다.** IP를 고정해 연결하면 둘이 구분된다.
- **"됐다"고 말하기 전에 명령을 돌린다.** 이 문서의 모든 수치는 실행 결과다.
